## 二、環境（三個一定會卡的地方）

1. **必須用 Python 3.12**，不能用 3.13。PaddlePaddle 沒有 3.13 輪檔。
   環境名 `pdfscan312`（conda），`start_webui.bat` 已寫死指向它。
   用錯版本不會報錯，只會**靜默降級成 VLM 直讀**——精準框全部消失。
   系統畫面「⚙️ 模型設定」下方會顯示地端 OCR 是否可用，部署後先看那一行。

2. **Windows CPU 需停用 oneDNN**。`ocr_engine.py` 已設 `FLAGS_use_mkldnn=0`，
   這是 paddle 3.3 + paddleocr 3.7 的相容性 bug，**別移除**。

3. **這些檔案不在版控**，clone 下來是空的，要另外跟原開發者拿：
   - `app/data/app.db`（憑證資料庫）
   - `app/data/uploads/`（憑證影像）
   - `app/data/accounts.json`（會計科目表）
   - `app/data/entry_examples.json`（分類 few-shot 種子）
   - `ref/TEST_DATA/`（客戶原始掃描檔）

   還需要本機 Ollama 並 `ollama pull qwen2.5vl:7b gemma4 bge-m3`。

## 四、踩過的坑（最重要的一節）

### 4.1 錯誤訊息會騙人：先印原始輸出再推測

三個案例長期「VLM 回傳非合法 JSON: line 1 column 1 (char 0)」。
`char 0` 字面上像「模型回了空字串」，我因此花了很久在**重試機制**上打轉。

真因是模型輸出裡有這些東西：

```json
"debit": 33,390.00,                          ← 千分位逗號（傳票金額格式）
"usage_fee": 2161 + 952 - (19 - 19) = 3124,  ← 模型在 JSON 裡寫算式
```

`json.loads` 從第一個字元起就無法構成合法 JSON，所以回報 char 0，**但問題在字串中間**。

**教訓：解析失敗時，第一件事是把模型的原始輸出整段印出來**，不要從錯誤訊息推測。
現在 `_parse_json` 有七層修復鏈（全形引號、註解、千分位、算式、尾逗號、單引號、補括號）。

### 4.2 提示詞範本裡的佔位值會被當範例學走

這個坑踩了三次：

| 範本寫法 | 模型行為 |
|---|---|
| `"amount": 0` | 分錄金額**全部填 0** |
| `"credit_account": ""` | 貸方**全部留空**，借貸不平衡 |
| `"debit": 0, "credit": 0` | （傳票）照抄版面的千分位格式 |

**寫 JSON 範本時，欄位值要放真實可用的範例值，不要放 0 或空字串。**

### 4.3 VLM 判「欄位歸屬」不可靠，座標交給 OCR

傳票的借方金額 120 被判到貸方，借貸就不平衡。**加提示詞規則完全無效**（試了兩輪）。
改用 OCR 座標判定就穩了：用表頭「借方金額」「貸方金額」的 x 中心取分界線，
再依金額實際印在哪個 x 位置決定借貸。借貸金額相同時（兩側都出現同一數字）
再用「與該列科目代號同一橫列」的 y 座標消歧義。

**這是本專案的核心分工原則**：OCR 管座標與字元精度，VLM 管版面理解與欄位歸屬。
遇到「位置」類問題，先想 OCR 能不能解，不要一直調提示詞。

### 4.4 沒有確定性就無法判斷改動有沒有效

固定 seed 之前，每案跑 3 次有 **6/16 案結果會變動**。那段時間我以為
「few-shot 種子有效、科目從 0→2→3」——**其實大半是雜訊**。

`temperature=0` + `seed=42`（`model_factory.RUN_SEED`）之後降到 **0/16**。

**副作用**：重試會拿到**完全相同的壞輸出**。若之後要讓重試有意義，重試時要換 seed
（正常辨識維持固定 seed 以保可重現）。這件事還沒做。

### 4.5 新增單據類型會吃掉既有正確判定

加 `bill_detail`（帳單明細附頁）時，第一版 Router 規則太寬，中華電信 4 頁**全部**
被判成附頁 → 整案零分錄，比原本的錯誤更糟。收窄後仍把「繳費結果通知」誤列為佐證，
但打開圖才發現**那頁印著繳費總金額與扣款帳戶，它就是入帳依據**。

**新增類型後一定要回歸測試既有類型**（`scripts/eval_dataset.py`），
別只驗證新類型有沒有被判對。

### 4.6 同一件事不要有兩套實作

`classify.py` 曾有自己的簡化版 `_parse_json`（只處理 code fence），與 `pipeline.py`
的完整版並存。修了 pipeline 那份，classify 還是壞的，qwen3 這類會在 JSON 後補說明的
模型 100% 解析失敗。已改為共用。

### 4.7 Windows 特有

- `cv2.imread` **讀不了中文路徑**（回 `None` 且不報錯）。頁圖檔名取自來源檔多為中文，
  等於電子發票 QR 解碼一直靜默失效。已改用 `np.fromfile` + `cv2.imdecode`。
- `.doc`（舊版 OLE）用 `win32com` 開 Word 讀取，`pypdfium2` 只能處理 PDF。

### 4.8 不要手動調 num_ctx

Ollama 0.32 已自動套用模型上限（qwen2.5vl:7b = 128K）。最壞情況（出口報單：
提示詞＋168 行 OCR grounding＋影像 ≈ 3,100 tokens）在預設值下輸出完整。
硬設 `num_ctx=16384` 只讓速度慢 4 倍（6s→23s），品質不變。

## 五、評估方法的注意事項

`scripts/eval_dataset.py` 的設計有幾個**刻意的選擇**，改動前先理解：

1. **標準答案是我們自己的傳票辨識產生的，會錯**。故有「答案品質閘門」：
   轉帳傳票必然借貸平衡，不平衡即為辨識錯誤，該案不列入計分。
   現支傳票（A931）只印支出面、貸方為現金隱含，單面才是正確的——別誤判為錯。

2. **以科目名稱比對，不比代號**。客戶傳票用仲彬 ERP 代號、系統依事務所科目表產出，
   代號本來就不同。另有等價對映表（花旗乙存→銀行存款等），明列在腳本裡並註明
   「暫定假設待客戶確認」。

3. **金額結構與科目分開量測**。兩表連名稱都可能不同（水電費／水電瓦斯費），
   混在一起比會分不出是萃取錯還是分類選了別的科目。

4. **多頁憑證分兩種**：多筆交易加總（加油 3 張發票）vs 同一筆交易的多份證明
   （中華電信：發票＋繳費通知＋明細）。後者各自產分錄再相加會讓金額翻倍，
   以「總額相同」判定只計一次。

### ⚠️ 誠實揭露：目前數字略為樂觀

除錯過程中曾**檢視測試組傳票的答案**（為了查明金額為何兜不攏、科目為何選錯），
據此寫入的規則雖屬台灣會計慣例、非本測試集獨有，仍使目前數字偏高。
**真正乾淨的驗收數字需要一組從未被檢視過的新資料。**

## 七、契約範圍的一個陷阱

`ref/` 有兩份文件，**範圍不同**：

| | 報價單（2025-04-09） | 委託技術服務契約（2026-01-07 簽） |
|---|---|---|
| 金額 | 第一期 60 萬＋第二期 60 萬 | 30 萬 |
| 第二期內容 | 平台建置＋**公有雲部署**＋**電子申報串接** | A1 正式版模組／A2 營業稅媒體檔／A3 第三期提案 |

**目前執行的是後者**（較晚簽的正式契約，期間 2026-07-01～2027-03-31）。
報價單第二期的公有雲部署與電子申報串接**不在現行契約內**，測試報告已載明此點。
若客戶提及這兩項，先確認是否為新案範圍。

另外報價單載明「辨識率期望值預計達 95%」，目前金額萃取 93%、科目相符 14%。
**驗收前務必先與客戶確認「95%」的量測對象與計算方式**——是欄位、金額還是科目，
定義不同結論天差地遠。
