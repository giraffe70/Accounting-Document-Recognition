憑證辨識系統 開發線上手冊

票據憑證單據掃描辨識軟體 — 將掃描 PDF／圖片萃取為結構化會計資料，經使用者確認後用於稅務申報。
Phase 1 完成 Phase 2 完成（除營業稅媒體檔） FastAPI + 混合 OCR/VLM 地端優先・可切換雲端 客戶：中意企業

本手冊記錄「憑證辨識系統」正式版程式碼（app/）的架構、模組、介面、帳號權限與現況限制，作為開發與交接的單一參考。第一期概念驗證 POC 已封存於 archive/phase0_poc_flask/。

💡 一句話理解
登入（記帳士／會計師／管理員）後依序使用四個頁籤：①匯入、②外觀確認、③掃描清單、④確認。外觀確認可修正類型、旋轉／裁切／分割影像；掃描清單可辨識、修正欄位及分類。修正先保存為草稿，再按「確認」完成；待確認／已確認是同頁篩選，預設待確認。只有已確認憑證進入日記帳、會計傳票與配對。

OCR 與 VLM 的分工

內容辨識採混合式：兩者各做最擅長的事，互補而非重複。OCR「看得準」（精確文字與座標），VLM「看得懂」（版面語意與欄位歸屬）。

面向OCR（PaddleOCR）VLM（qwen2.5vl）
角色精準的眼睛：讀出文字＋每行精準座標理解的大腦：看懂版面、判斷欄位歸屬
輸出每行文字 + bounding box結構化 JSON（哪段文字＝哪個欄位）
強項統編／金額數字精確、框座標精準版面理解、欄位歸屬、單據類型判斷
弱項不懂結構（不知數字是統編還金額）數字易看錯、給的框座標不可靠

協作順序（extract_for_type）：① OCR 先跑取得文字與精準框 → ② VLM 收「原圖＋專屬提示詞＋OCR 文字（grounding，數字以圖為準）」輸出欄位歸屬與粗略框 → ③ 框精修（_refine_boxes_with_ocr）把每個欄位值比對 OCR 行，對上就換成 OCR 的精準框； 值橫跨多行時（報單的出口人＝中文名＋英文名＋地址三行、日期已轉西元但單據印民國）退階以最長片段定位， 但退階候選須唯一命中才採用，命中多行代表不夠獨特，寧可不給框 → ④ 條碼/QR（OpenCV）有 QR 直接解，電子發票 QR 為權威值。

💡 為何不單用一個
單用 VLM：結構懂但統編/金額常誤判、框亂飄，財務不可接受；單用 OCR：字與座標準但只是一堆散字、無結構。 合起來＝OCR 的「準」補 VLM 的短、VLM 的「懂」補 OCR 的短。框的精準度由 OCR 負責、VLM 的框僅備援——故密集報單只保留 OCR 驗證過的框（寧缺勿錯）。OCR 另兼自動轉正（四方向信心度擇優）。
🛠️ 模型切換設計
沿用 research_log_agent 模式：每階段以 provider/model 字串存於 settings.json，經單一 model_factory 分支（ollama/google/anthropic/openai，皆走 LangChain）。未設雲端金鑰時，雲端選項自動隱藏，純地端可運作。

支援的單據類型（Router → 專屬 agent）

由 doc_router 判類型後，交給該類型在 doc_types.DOC_TYPES 的專屬提示詞與欄位契約辨識。 目前登錄 18 種文件類型，共用模板搭配各類型欄位契約與提示。 共用辨識模板與欄位契約見 〈辨識模板與資料契約〉。

🤖辨識模板與資料契約

辨識流程共用三個核心模板：路由分類、欄位萃取、會計分類。18 種文件各自提供欄位契約與 type_hints，不再維護每種文件的一整份獨立提示詞。

辨識流程

flowchart LR IMG["頁面影像與 OCR"] --> ROUTE["路由模板"] --> TYPE["文件類型與契約"] TYPE --> EXTRACT["萃取模板"] --> READ["共用補讀與欄位檢查"] --> REVIEW["待確認資料"] REVIEW --> ACCOUNT["會計模板"] --> CANDIDATE["候選分錄"]
路由與萃取共用提示詞模板，再以文件類型契約和提示補充差異；會計模板產生供審核的候選分錄。

欄位契約失敗時，系統會保留原始訊息，在初次請求後再做 1 次契約重試；重試將靜態 system 指示併入第一個 system 訊息（保留原任務前綴），錯誤另作 user JSON，原 user 證據不變；每一輪傳輸最多重試 3 次。影像補讀與輸出修正由共用流程處理。

條碼或 QR 解碼值若與影像辨識欄位衝突，保留衝突警告供後續檢視，不靜默覆蓋其中一方。

固定任務規則由 system 訊息承載；OCR、備註、政策、案例及其它輸入資料以 user JSON 資料區傳入，不因此取得指令權威。選取證據只表示本次送交內容，不等於人工確認。

③ 會計模板（ACCOUNTING_TEMPLATE）

只對已確認為進口的文件套用進口規則；出口類型不套用。預設角色映射為：進口稅費→預付費用、海關營業稅→進項稅額、銀行手續費→其他費用。未付款進口／商品使用應付帳款，一般未付款費用使用應付費用；已付款須有付款方式，才能選銀行存款或現金。科目角色由當次公司的科目表解析，不固定寫入科目代碼。進口預設 include_goods_values=false、posting_currency=TWD；外幣發票與明細完整保留，但不將外幣貨款與臺幣稅費混合加總。

手寫／潦草憑證的人工作業流程

手寫三聯式等憑證超出地端 VLM 的可靠範圍（實測「1575」讀成「1525」、統編末兩碼讀錯，且每次結果不同）。 這類憑證的正確作法不是反覆重辨識，而是人工鍵入並留下軌跡：

  1. 先看紅字：系統以確定性檢查標出可疑處——統編檢查碼、日期合理性與 OCR 日期／發票期別交叉核對（民國轉西元算錯會讓憑證從當期報表消失）、金額算術（未稅＋稅額＝總計、應稅 5%）。紅字所在就是要核對的欄位。
  2. 對照原圖逐欄改正：點欄位左側色塊可在影像上定位；手寫金額以「總計新台幣（中文大寫）」為準，大寫比阿拉伯數字好認。
  3. 勾選「✍ 人工修正」：表示這張的欄位已由人工編輯確認。清單會出現 ✍ 標記，「🐞 修正回饋」頁也會列入；日後有人按「重新辨識」會先跳提醒，避免覆蓋。
  4. 備註寫下判讀依據（如「總計 1575 依中文大寫」）：備註同時會成為下次辨識的修正提示。
  5. 💾 儲存修正：ai_json 保留 AI 原值不動，current_json 存人工值，兩者差異即修正軌跡（模型對齊訊號）。
🚨 重新辨識會覆蓋人工修正
recognize_record 會同時改寫 ai_json 與 current_json——手工鍵入的值會被模型輸出蓋掉。 故整理完請勾「✍ 人工修正」——勾選後再按重新辨識會先跳確認。（刻意不用「值有沒有變動」當觸發條件：存過一次就不同了，天天跳提醒反而會被無視。）

外觀確認（匯入後、內容辨識前）

為降低「影像未轉正／類型誤判」造成的欄位框錯位，辨識拆為兩階段：匯入只做外觀準備（Router 判類型 + OCR 自動轉正，狀態 prepared）， 使用者在審核畫面先確認外觀，按「✅ 確認並辨識」才依確認的類型萃取欄位與精準框。此時審核欄位區塊隱藏，只保留影像與整理工具。

🚧現況限制與部署陷阱

🚫 尚未完成
  • 營業稅媒體檔 TXT／TET_U + 401：財政部電子申報特定格式，需範例檔/規格才能正確產製，硬猜會產出無法轉入的檔。
⚠️ 部署與資安注意
  • 種子帳號為預設密碼，正式使用前務必更改。
  • session token 存於記憶體，伺服器重啟需重新登入。
  • 出錯先看日誌：app/data/logs/app.log（滾動 2MB×5）保有辨識／分類失敗的完整 traceback；畫面上的錯誤對話框只給摘要。
  • PaddleOCR 需 Python ≤3.12，故整個應用鎖在 pdfscan312；換機若漏建此環境會降級為 VLM 直讀（統編/金額準確度略降、精準框消失）。「⚙️ 模型設定」的 OCR 欄位下方會顯示地端 OCR 是否可用，部署後先看這一行。
  • 弱地端模型（如 gemma）分類偶有借貸不平衡，系統會紅字標示待人工核對；建議分類用 qwen2.5。
  • 手寫憑證（如手寫三聯式發票）超出地端 VLM 的可靠範圍：實測手寫「1575」被讀成「1525」、統編「23051677」讀成「23051697」，同一張多次辨識結果還會變動。強化提示詞無效（反而更糟），故改以確定性檢查把錯誤標出來——統編檢查碼、日期合理性、金額算術（未稅＋稅額＝總計、應稅 5%）。這類憑證務必人工核對金額。
  • 民國轉西元算錯是最危險的錯誤：日期錯 → period 跟著錯 → 該憑證從當期日記帳與報表中無聲消失。提示詞要求模型照印出原文輸出日期、不得自行換算年份，民國換算只由程式執行（西元＝民國＋1911）；系統另以 OCR 讀到的民國日期與發票期別（如「115年7、8月份」）交叉核對，不一致時在日期欄旁標紅待覆核（不自動改值），並保留合理性檢查兜底。
  • 雲端 VLM/LLM 會將憑證上傳第三方；敏感財務資料建議維持地端優先。
